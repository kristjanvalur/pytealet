# Channel timeout hand-off

A channel rendezvous commits the transfer before the parked peer resumes. A `RawTimeoutError` delivered into that peer splits the two sides: one call has already returned success, and the other would raise. The value cannot be put back.

## What is committed

`receive`, finding a parked sender, pops the packet out of the channel and returns it. The sender is only queued. A throw into that sender cannot put the packet back. It is in the receiver's frame, or already with the receiver's caller.

`send`, finding a parked receiver, stores the packet and returns. That return is the sender's success. A throw into the receiver then fails `receive` without failing `send`. Dropping the packet loses the message.

Rolling the transfer back is not available once the other call can observe it.

`cancel()` and any other `Task.throw` land immediately. They are not postponed. Cancelling is a terminal signal, and delaying every exception would hide that. An exception injected into `send` or `receive` by `timeout()`, `cancel()`, or another `Task.throw` carries `operation_result`, a `(success, value, exception)` triple. It did not originate with the sender. A `send_exception` payload raised by a normal `receive` does not carry the attribute. It originated with the sender. `success` is true once the packet has moved. On `receive`, `value` is the object and `exception` is `None`, or `exception` is the instance passed to `send_exception` and `value` is `None`. That payload still has no attribute of its own. On `send` both are `None`. The channel has dropped its own copy. A caller that still needs the object reads the triple and re-raises that exception. A sender puts the object back on its own queue only when `success` is false. `tealetio.examples.send_or_requeue` is that handler, and the Channel section of `PYTHON_API.md` shows the call. After the packet has moved, cancelling the sender leaves the value with the receiver and fails `send`, so a retry delivers a second copy. Cancelling the receiver puts the object on that exception. A waiter cancelled before anyone takes the packet reports `success` false, and the offer is dropped. The channel stays usable afterwards.

`Event`, `PulseEvent`, and `CrossThreadEvent` do not have this gap on their own. A timeout that ties with `set()` propagates. Nothing in `set()` has been handed to another caller. A transfer that wants a timeout to wait until both sides have observed the object opts into the atomic flag.

## Atomic flag

`Task` keeps a depth count. `atomic_inc` adds one, including on a different task. `atomic_dec` removes one. `in_atomic` is true while the count is nonzero. `atomic_restore` does not add a level. On exit the count is whatever it was on entry, so several `set` calls can increment it across several waits inside one block, and leaving the block drops all of those levels. A level held before entry stays. The count must not fall below the entry value. An exception inside the block propagates, and the count is still restored on the way out.

The count does not catch exceptions and does not postpone them. `Task.throw` and `cancel` land immediately. `timeout()` is a control-flow policy that reads `in_atomic` and, while it is true, arms the same timer again with `call_later(0)` instead of delivering the throw. The timer has still fired: `_expired` is set, and `reschedule` will not move it.

`AtomicEvent` applies that pair. `set` calls `atomic_inc` on each parked task before it wakes them, and rolls those levels back if `set` raises. `swait` is `atomic_restore` around `Event.swait`. A task that arrives after `set` finds the flag already set, so it is not marked. `Event.set` does not suspend the caller, and neither does `AtomicEvent.set`, so the caller holds no atomic level of its own. The synchronous wait is `swait`. `Event.wait` is the asyncio future and is not this park. The task methods stay public for a transfer that parks on something else.

`Rendezvous` in `tealetio.examples.misc` illustrates a one-slot exchange. It is not a library primitive, and it does not use the atomic flag. The sender treats the object as delivered only after the receiver has accepted it. The side that arrives first creates the hand-off and parks on a plain `Event`. The sender, if it arrives second, writes the object into that hand-off and parks until the receiver answers. A normal wake is acceptance: the receiver records that answer and returns the object. If the receiver is resumed by an exception after the object was handed over, it answers with rejection and the sender raises `RuntimeError`. If the sender is resumed by an exception before it sees an answer, it raises that exception and does not report delivery. The receiver may still take the object. A timeout while one side is still the only waiter withdraws the offer. Postponing `timeout()` or `cancel()` is not part of this protocol. The slot is cleared before the arriving sender waits for the answer, so the next exchange can start once the receiver has left the call. On the success path, `Event.set` only queues the waiter, so the receiver observes the object before `send` returns. A `timeout(0)` around `send` can fire in that answer wait: the driver is often ahead of the queued receiver, the throw lands before the receiver runs, and `send` raises without reporting delivery. The receiver then still takes the object.

The channel uses the same pair. It does not mark the wait itself. After the packet has moved, the wake calls `atomic_inc` on the parked task, which may already be inside some other section. Async `send` and `receive` use that wake with immediate transfer off: a parked tealet is marked and only made runnable, and an `Event` waiter is not marked. The parked task restores the entry count with `atomic_restore` when its park returns. Preference decides whether the committer then runs the peer immediately. That switch suspends the committer, so the same wake holds the committer in `atomic()` until `run()` returns. Negative preference does this on send. Positive preference does it on receive. The atomic operations do not swap. Only which side remains suspended does. `Event.set` does not need `atomic()`, because the caller of `set` keeps running. `atomic()` adds one level and removes it on exit. Levels a peer adds during the block must already be gone, which `atomic_restore` does for a wait inside it. The marker covers the gap in which one side has committed and the other has not yet resumed past the rendezvous.

The re-armed timer is not in the list this drain already popped, so it waits for a later drain. A batch drains once, before its tasks, so that later drain is the opening of the next batch. When the task is still parked and not runnable, the attempt can still see the marker and arm itself once more. The parked task runs after that drain and clears the marker. The opening drain of the batch after that resume delivers the throw. Both sides have observed the transfer by then.

`Timeout.__exit__` cancels the current handle. That is the re-armed timer when the deadline has already fired, so a block that ends before the later drain does not throw. A `timeout()` wrapped only around the rendezvous therefore still succeeds when the timer ties with the commit. `expired()` stays true, because the timer did fire. If the hand-off finished before the timer ran, the original handle is cancelled and `expired()` stays false. An outer `timeout()` that continues past the rendezvous is still open, so the throw lands on the next park inside that block. `reschedule` does not extend a timeout once it has fired.

`timeout()` is what withholds the throw. The channel does not catch `RawTimeoutError` and does not read the atomic count. While the mark is set, a committed `send` or `receive` returns normally and the timeout lands on a later park. `Task.throw` does not consult the marker, so `cancel()` and a direct throw still land in the wait. The call raises, and `operation_result` says whether the packet had moved.
